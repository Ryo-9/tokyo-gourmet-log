# TOKYO GOURMET LOG — 開発引き継ぎ（2026-11-18）

## ゴール
「自分の食べ歩き記録」から、友達・グループ・街の投稿を通じて新しい店を発掘し保存できるサービスへ段階的に拡張する。初期230店舗の検索・訪問記録・地図機能は維持する。

- GitHub Pages: https://ryo-9.github.io/tokyo-gourmet-log/
- Repository: https://github.com/Ryo-9/tokyo-gourmet-log
- Branch: `main`
- 関連資料: [ROADMAP](../ROADMAP.md) / [グループRLS検証](GROUP_SECURITY_TESTS.md) / [Supabase導入記録](SUPABASE_ROLLOUT.md)

## 現在の実装
- 個人の「行きたい」「訪問済み」「訪問日」「感想」「写真」を端末に保存
- 230店舗＋追加店舗の検索、Leaflet/OSMによる本人操作型周辺検索、マイマップ（確認済み座標のみ）
- 画像OCR・リンク解析による店舗発見補助
- ログイン不要の共有リスト（URLスナップショット＋ローカル投票/返事、オンライン集計ではない）
- Supabaseメールログインと手動クラウドアップロード/不足分取り込み（β）
- 招待制オンライン・グループの作成・承認・候補店追加・投票・退会・作成者によるグループ削除（β）

## インフラ状態（2026-11-18に再確認）
- Supabaseプロジェクトは ACTIVE_HEALTHY（東京リージョン）。
- `tgl_*` テーブル9件はすべてRLS有効。
- グループ5テーブルのRLSポリシーは合計19件（4+3+4+4+4）。
- グループ5テーブルの行数はそれぞれ0件（SQL内ROLLBACKテストのみで実利用データなし）。
- SQL上で3権限を切り替えるテストは完了。2台のiPhone間のE2E検証は未完了。
- 旧音楽アプリに関係する `public.add_owner_as_song_member()` の実行権限警告（匿名・ログインユーザー）と、漏えいパスワード保護無効の警告は残る。**既存アプリへの影響調査なしに関数を削除・変更しない**。

## 現時点の制限と守るべき方針
1. クラウドは明示的な手動同期。写真/IndexedDB、SNSリンク、共有リストは同期しない。端末内の店舗JSONと写真は別途バックアップ。
2. 同一IDのクラウドアップロードは上書きとなり得る。複数端末間で編集競合を自動解決しない。
3. グループデータはログイン/承認が必要。ユーザーコードは相手から受け取り、勝手にメール・名前から探索しない。グループ票の表示は「更新」操作後。
4. 個人の訪問ログ・写真・行動履歴・正確な現在地はグループ参加により共有されない。公開投稿はまだ無効。
5. すれ違い（Sway型）は構想段階。本人同意のない位置追跡やリアルタイムの人の特定をしない。
6. GitHubの公開リポジトリにservice_roleキー・シークレット・認証トークン・本名/メール・私的な食事記録/写真を書かない。

## iPhoneの操作が可能になったら
1. 「設定」から先に店舗/訪問履歴JSONと写真を個別バックアップする。
2. 既存メールアカウントでログインし、少量のテスト店・訪問履歴をクラウドへ手動保存する。
3. 別ブラウザ/端末で件数プレビュー・不足分取り込みを確認。既存データの非破壊性と重複なしを確認する。
4. 別アカウントの協力者と `つながる > グループ` で作成・ユーザーコード交換・招待・承認・投票・「更新」・退会を試す。
5. テスト結果と失敗画面をIssue #1/#2へ追記。認証情報、プライベートな食事履歴は貼らない。

## iPhoneが操作できない間に進められること
- 公開/非公開設定、友達申請・承認、投稿削除・通報・ブロックの仕様書作成
- RLSを含む回帰テストのコード化、グループ・フィードのモバイルUI改善
- クラウド同期の競合/削除扱いの設計、写真Storageのプライベートバケット案検討
- 既存音楽アプリのSecurity Advisor警告に関する**読み取り専用**監査
- GitHub上のコード・ドキュメント更新は可能。ただし実ユーザーの端末状態・認証済み操作・複数人E2Eを完了したと主張しない。
